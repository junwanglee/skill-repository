# Java Docker 线上性能自主诊断

Use this skill to guide a safe, evidence-based diagnosis of one Java 8 service in one Linux Docker container. Arthas is the only JVM diagnosis tool. SSH must reuse the operator's existing configuration. Password or keyboard-interactive authentication may prompt in the operator's local terminal; SSH key authentication is also supported.

All messages shown to the operator—including menus, progress updates, approvals, errors, and completion summaries—must be in Simplified Chinese. Preserve literal commands, paths, identifiers, and error text, and explain them in Chinese.

## Hard safety boundaries

- `SKILL.md` is the current product workflow. `docs/design.md` is the original historical design and does not override this file. The operator's explicit selection of a server, container, and Java process/PID confirms that target; do not ask for a redundant final confirmation of the same tuple.
- **Mandatory choice-and-pause rule:** for every choice, use the host application's native single/multiple-choice UI when available (for example, clickable options). Do not require the operator to type an option number. In text-only clients, show labeled options and accept the option label or a short free-text equivalent. Ask only the current question, then end the turn and wait. Never ask the user to type an IP/name when discovered options are available. Require explicit selection even when there is only one option; never infer consent from silence or a prior run.
- Production diagnosis does not change business data, code, configuration, JVM options, container configuration, or service state. Never restart/stop/kill a service, elevate with sudo, change mounts, rebuild a container, or bypass host-key/security controls.
- Never read, copy, or upload SSH private keys. Do not ask the operator to send a password in chat or enter it into a Skill prompt/script. For first-time SSH password authentication, let the local OpenSSH client prompt directly in the operator's terminal; the password must not enter agent context, command arguments, logs, or files. Do not dump all environment variables or read unrelated business files; redact secrets in captured output.
- Only use L1 commands automatically after target confirmation. L2 profiling/instrumentation must have a narrow target and bounded duration/count/output; default profiler duration is 20 seconds and the operator may choose up to 5 minutes (300 seconds), with no segmented runs to bypass this per-task cap. At most one active sampling task per JVM. Before offering or starting **any L2 command** (`profiler`, `trace`, `watch`, `monitor`), check host/container recent OOM and container memory against its limit. If the host or target container had a recent OOM, or current container memory is at least 80% of its limit, L2 is disabled by default. Show the risk and offer L1/defer as the recommended choices, plus an explicit **“强制启用 L2（承担风险）”** exception option. The exception requires a separate, fresh confirmation that states the observed OOM/memory condition, exact L2 operation, target, duration/count, and stop plan; do not treat generic approval or a prior approval as this confirmation. If selected and confirmed, proceed only within the approved bounds and record the risk acceptance in the task ledger and report. Never imply that confirmation removes the operational risk. Never combine profiler sampling with repeated dashboard polling in the same run. Stop L2 before continuing. L3 (heap dump, runtime mutation, potentially long STW or similarly high-risk operations) is not executable by this skill; explain the risk and stop.
- Do not invoke arbitrary shell supplied by the user or compose a command from unvalidated values. Use the documented commands in `references/` and validate identifiers. If a safe, bounded command cannot be formed, stop and explain.
- Use only container-existing writable temporary paths. Attach/runtime temp and report output paths are distinct capabilities and must be checked separately. Never add a mount, change read-only settings, or change permissions to enable diagnosis.
- Stop and reconfirm if the container ID or JVM PID changes, the container restarts, or the target becomes ambiguous.
- If a diagnostic attempt causes an OOM, container exit, or restart, stop all profiling and further intrusive work immediately. Gather read-only evidence, report the impact in Chinese, and do not automatically switch to a replacement replica or retry.

## Workflow

1. **Select the server first.** Run `scripts/check-local-ssh.sh` and `scripts/list-ssh-servers.sh` to inspect local configuration only. Do not connect or probe any host before selection. The list script resolves local SSH settings only; show each literal Host entry, including IP-valued entries, with alias, resolved host, user, port, and “not tested.” If there are no entries, offer guided setup or a complete setup command. Ask the operator to select one server using the native choice UI when available; otherwise accept its label. Pause.
2. **Select the diagnosis direction.** After server selection and before connecting, ask one separate question if the direction is missing. Offer CPU, interface latency, memory, GC, thread/blocking, or “uncertain / start with baseline.” If the request already names a direction, show it as the recommended choice and let the operator select it or another direction. Do not ask for the server again. Pause.
3. **Connect and list containers.** Connect only to the selected alias. First run local `ssh -O check <alias>`; if a ControlMaster is active, reuse it and do not ask the operator to authenticate again. Only when the master is missing/expired and key authentication cannot connect, explain in Chinese that one local password login is needed, provide `! ssh <alias> true`, and pause. Never ask for a password in chat or a Skill prompt. New aliases created by the setup script persist for one hour; existing aliases retain their configured duration. Do not close the master at task completion by default; let it expire, unless the operator asks to close it. Stop on authentication failure without repeated retries. Check Docker without sudo, list all running containers, and ask the operator to choose one using native options or its label. Pause before inspecting container processes.
4. **After container selection, identify Java services/processes.** Inspect only the selected container. Enumerate every Java PID with Jar/main class, Java version, and user when available. Present these as choices and **PAUSE** for explicit selection (one process still requires selection). If none are found, explain what was checked and stop; do not switch containers automatically.
5. **Proceed with the selected JVM.** The operator's Java service/PID menu selection completes target confirmation; briefly restate the chosen server/container/service/PID for visibility, then continue to compatibility checks without asking them to confirm the same target again. Stop and repeat the relevant selection only if identity changes.
6. **Check compatibility and offer diagnosis methods.** Assess OS/architecture, actual JVM Java path/version, Java 8 JDK `tools.jar` availability where required, UID/GID, attach permissions/namespace, JVM attach settings, container limits, available disk and writable directories. Check recent host/container OOM and current container memory before showing L2 methods. Present choices with a recommendation, what each measures, expected impact/output, and approval requirements. If a recent OOM or memory >=80% is detected, recommend L1/defer and show the explicit force-L2 exception option with the observed risk; its selection must lead to the separate risk confirmation in step 9. Pause.
7. **Prepare Arthas only after compatibility passes.** Run `scripts/prepare-arthas.sh`. If local cache is absent, it downloads `https://arthas.aliyun.com/arthas-boot.jar`, verifies the JAR manifest is version 4.3.5, then stores it under `~/.performance-diagnosis/arthas/versions/4.3.5/` with a local SHA-256 record. If cached, it checks that record before use. The first digest is learned from the first HTTPS download, not an independent publisher signature; do not claim signature verification. Transfer local→host via SCP and host→container via Docker CP using a unique task directory; remote host/container need not access the internet.
8. **Plan and announce collection.** Before execution, state the selected method, command families, limits, and exact local output paths. Local Arthas cache is `~/.performance-diagnosis/arthas/versions/4.3.5/arthas-boot.jar`; local task ledger is `~/.performance-diagnosis/tasks/<task-id>.state`. Local evidence and report go under `~/.performance-diagnosis/diagnostics/<host>/<container-id>/<task-id>/` (including raw logs, `environment.md`, and `report.md`). These paths must resolve on the operator's real local machine; if the Agent runs in a sandbox or container, establish the mapped writable path first. Remote staging uses `/tmp/pd-<task-id>/` on host/container when that existing location is writable; never create it by changing mounts or permissions. If paths differ due to environment constraints, state actual paths and pause before L2 sampling. Before starting, inspect the local task ledger and recover unfinished tasks. Use `scripts/arthas-batch.sh` for bounded L1; it auto-downloads/cache-prepares Arthas when `--arthas-boot` is omitted.
9. **Let the operator set sampling parameters and confirm exceptions.** For repeated L1 sampling, ask duration first (recommend 1 minute; offer 3, 5, 10 minutes or a custom value up to 10 minutes), pause, then ask cadence (recommend 10 seconds; offer 5 or 30 seconds). For L2 profiler, distinguish sampling interval from total duration. Arthas CPU profiler defaults to 10 ms per sample; offer 10 ms (recommended), 20 ms, or 50 ms, explaining that a longer interval lowers sample frequency/overhead but also reduces detail. Ask separately for total duration (recommend 20 seconds; offer 1/3/5 minutes or a custom value up to 300 seconds). Never split a longer request into multiple runs to bypass the 5-minute per-task cap. By default, save both `profile.md` for AI-readable hotspots/call tree and `flamegraph.html` for visual inspection when the operator-approved output path supports both; if only one artifact can be safely produced, explain the limitation and offer a choice. Show output location and stop plan. For the force-L2 exception, first display the current OOM/memory evidence and selected operation, then ask for a separate explicit confirmation that the operator accepts this specific elevated risk; pause and wait. Record the accepted risk and evidence in the task ledger/report. Use native choice controls when available; otherwise accept Chinese labels. Never begin sampling until parameters are selected and all required approvals are received. Ensure only one active task per JVM.
10. **Collect and return artifacts.** Prefer an existing writable container temp or existing writable mount, then `docker cp`/SCP. Text that Arthas can safely emit to stdout may be captured there. Do not attempt file-based profiling when no safe output path exists. Verify file size and SHA-256 after transfer; on failure retain remote artifacts and record recovery details.
11. **Stop and clean up this task only.** Send the documented stop operation for any active profiler, then issue Arthas `stop`/detach for this session and verify it has exited. Update the local record with `scripts/arthas-task.sh finish --task-id <id> --result completed|failed|stopped`. Remove only files created under this task's unique directory after successful local verification. Never kill an unknown process or delete another task/session's files. If cleanup cannot be safely attributed, leave it and report.
12. **Write the report.** Use `templates/performance-report.md`, include evidence, uncertainty, unavailable checks and artifact list. For every root-cause candidate, name the exact class/method and, when source is available, repository/file/line plus the relevant code behavior; connect it to profiler/trace/thread evidence and give a concrete, prioritized optimization proposal with expected trade-offs and a validation plan. Distinguish directly inspected source from inference. If source code/revision is unavailable, say so and provide the precise class/method/stack to inspect; never invent repository paths or line numbers. Save under `~/.performance-diagnosis/diagnostics/<host>/<container>/<task-id>/` with restrictive permissions. Redact secrets.

13. **Respect source access boundaries.** Only inspect source repositories/workspaces already available to the operator or explicitly provided for this diagnosis. If application source is not available locally, do not search arbitrary disk paths or expose unrelated repositories; report the class/method and request the relevant repository/commit when code-level confirmation is needed.

### Required interaction pattern

The pauses above are control-flow requirements. Prefer native choice controls so the operator can select an option instead of typing a number. In text-only clients, show concise labels; accept a label, a brief phrase, or a custom answer where applicable. Ask exactly one question and stop. Do not combine server selection, diagnosis direction, password login, container selection, Java PID selection, method selection, or sampling parameters in one turn. The server, container, and Java PID choices confirm the target; do not add a duplicate confirmation. Before collection, tell the operator where the Arthas cache, remote temporary files, local evidence and report will be stored.

When the host provides no choice UI, use a compact Chinese text menu such as:

```text
我在本机 SSH 配置中找到以下服务器（尚未连接）：

• staging — ops@192.0.2.20:2222

```

## Command tiers

- **L1, low-impact read-only:** Arthas `dashboard`, `thread`, `jvm`, `memory`, `version`; Docker `ps`, `inspect`, `stats --no-stream`, bounded `logs --tail`; Linux `uptime`, `free`, `df`, `ss -s`; bounded `vmstat`. Run only against the confirmed target. Repeated L1 sampling may run up to 10 minutes with an operator-selected cadence.
- **L2, controlled instrumentation:** `trace`, `monitor`, `watch`, `profiler start/stop`. Use only with a scoped target and enforceable caps. No unbounded wildcard matching.
- **L3, prohibited in v1:** heap dump, dynamic class/VM mutation, JVM option changes, service/container lifecycle actions, or any operation likely to cause large pauses/resource spikes.

## Scope of v1

Supports Linux Docker Java services, SSH password/keyboard-interactive or key-based access, one host/container/JVM per run, and Arthas as the JVM tool. It does not support bare-metal Java, Kubernetes, parallel diagnosis, automatic fixes, heap dumps, or automated production configuration changes.
