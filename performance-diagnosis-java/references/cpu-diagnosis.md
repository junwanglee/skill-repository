# CPU 偏高诊断

1. 先记录宿主机负载、容器 `docker stats --no-stream` 与 JVM `dashboard`，区分主机压力、容器配额/节流和 JVM CPU。
2. 使用 `thread -n 10` 识别热点线程，保留线程 ID、状态、栈和采集时间；重复短间隔采样确认持续性，不以单次快照定论。
3. 只有目标仍确认且 L1 证据指向 JVM 计算热点时，才做有界 profiler 采样。先检查容器内存余量及近期 OOM；内存使用达到 limit 的 80% 或近期发生 OOM 时，不运行 L2。Arthas CPU profiler 默认采样间隔为 10 ms；执行人可选择 10/20/50 ms。间隔越长，采样频率和开销越低，但细节也会减少。总时长默认 20 秒，执行人可选最长 5 分钟（300 秒）；每个任务不得拆段规避上限。不要与重复 dashboard 采集并行运行。
4. 输出优先选择 Arthas 4.3.5 支持的 Markdown profiler 报告，以便 AI 直接读取热点和调用树；如同一采样数据可安全导出 HTML，也保留交互式火焰图。若该固定版本无法对同一份采样数据安全提供两种格式，向执行者说明并选择 Markdown（默认）或 HTML，不能为补格式重新采样。没有既有可写输出位置时跳过文件型采样，采用低开销文本检查并报告限制。
5. 分析热点占比、调用树、线程和业务代码证据。将热点映射至仓库版本、类、方法、文件和行号；针对代码说明触发路径、具体耗时/分配行为，并提出带优先级、收益/风险取舍及验证步骤的优化建议。若无法读取对应源码，只输出火焰图中的类/方法/调用栈并标为待源码核实，不编造文件或行号。说明采样代表性及负载条件；不要把采样关联直接表述为已证明的根因。
