# Java Docker 线上性能自主诊断 Skill 详细设计方案

> **状态：历史原始设计，不作为当前实现的验收基线。** 当前产品行为以 [`../SKILL.md`](../SKILL.md) 和 references 下的执行规范为准。本文保留最初设想以供追溯；与主流程冲突的部分尚未全部重写。

**项目名称：** Production Performance Diagnosis  
**项目类型：** AI Agent Skill  
**核心诊断工具：** Alibaba Arthas  
**目标环境：** Linux + Docker + Java 8  
**远程连接：** SSH 免密登录  
**本地缓存目录：** `~/.performance-diagnosis`  
**设计版本：** V1.1  
**文档状态：** 待审核通过

---

# 一、项目背景与目标

## 1.1 项目背景

线上 Java 服务出现性能问题时，通常需要开发人员登录服务器，手动执行 Linux、Docker、JVM 诊断命令，再结合 Arthas 分析线程、CPU、内存、GC、方法耗时等问题。

这一过程依赖开发人员对 JVM、Linux、Docker 和 Arthas 的熟悉程度，排查步骤较多，问题定位效率也容易受到个人经验影响。

希望通过开发一个专门的 AI Skill，让 AI Agent 具备自主执行线上 Java 性能诊断的能力。

执行人只需要选择服务器、容器和问题类型，AI 就可以按照预设的诊断流程：

1. 检查本地 SSH 免密登录配置。
2. 选择需要排查的远程服务器。
3. 自动发现服务器上的 Docker Java 容器。
4. 识别容器内部的 Java 进程。
5. 完成 Java 环境和 Arthas 兼容性检测。
6. 自动准备 Arthas 并 Attach 目标 JVM。
7. 根据问题类型执行对应的诊断命令。
8. 分析诊断结果，必要时继续深入排查。
9. 将所有诊断结果保存并回传到本地。
10. 生成详细的性能诊断报告。

## 1.2 项目目标

- 降低线上性能问题的人工排查成本。
- 将常见 JVM 性能诊断流程标准化。
- 让 AI 根据不同问题自主选择 Arthas 命令。
- 保留完整的诊断过程和原始数据。
- 通过证据分析问题，而不是仅凭经验猜测。
- 诊断过程安全可控，不修改生产环境业务状态。

## 1.3 核心设计原则

| 原则 | 说明 |
|---|---|
| 单一诊断工具 | 只使用 Arthas，不引入独立的 async-profiler 等诊断工具 |
| 环境优先 | 先检查环境，再执行诊断 |
| 人工确认 | 服务器、容器、JVM PID 等关键对象由执行人确认 |
| 自主诊断 | AI 根据问题类型自主规划诊断步骤 |
| 生产只读 | 不修改业务代码、配置、数据及服务运行状态 |
| 证据驱动 | 所有根因结论必须有诊断数据支撑 |
| 本地缓存 | Arthas 在本地统一下载和管理 |
| 远程临时部署 | 工具按需复制到远程容器，诊断后清理 |
| 完整留痕 | 诊断命令、原始结果、分析报告统一保存 |

# 二、整体架构设计

## 2.1 架构组成

整个 Skill 分为五个模块。

### 模块一：本地环境管理

负责：

- SSH 客户端检测。
- SSH Key 检测。
- 免密服务器发现。
- 新增服务器引导。
- 本地 Arthas 缓存管理。
- 诊断结果目录管理。

### 模块二：远程服务器管理

负责：

- SSH 连接。
- 服务器基础信息采集。
- Docker 环境检测。
- Docker 容器列表获取。
- 目标容器选择。

### 模块三：Java 环境与兼容性检测

负责：

- 容器内 Java 版本检测。
- Java 进程识别。
- JVM PID 确认。
- JVM Attach 能力检测。
- Arthas 运行条件检查。
- 诊断文件输出能力检测。

### 模块四：Arthas 诊断引擎

负责：

- Arthas 下载与版本管理。
- Arthas 远程部署。
- Attach 目标 JVM。
- Arthas 命令执行。
- 诊断任务管理。
- 诊断数据采集。

### 模块五：AI 分析与报告

负责：

- 问题分类。
- 诊断策略选择。
- 诊断数据分析。
- 根因判断。
- 优化建议。
- 诊断结果回传。
- 诊断前后对比。

# 三、SSH 服务器管理

## 3.1 本地 SSH 环境检测

Skill 启动后，首先检查本地 SSH 环境。

检查内容：

1. 是否安装 SSH 客户端。
2. 是否存在 SSH 配置目录。
3. 是否存在 SSH 密钥。
4. 是否存在 SSH Config。
5. 是否存在 SSH Agent。
6. 哪些服务器可以免密登录。

重点检查：

- `~/.ssh/config`
- `~/.ssh/id_ed25519`
- `~/.ssh/id_ed25519.pub`
- `~/.ssh/id_rsa`
- `~/.ssh/id_rsa.pub`

不能仅凭 SSH Key 文件存在就认为已经配置了免密登录，必须通过实际连接验证。

## 3.2 发现已配置免密登录的服务器

读取本地 SSH Config：

```bash
cat ~/.ssh/config
```

示例：

```sshconfig
Host beta
    HostName 192.168.1.100
    User root
    Port 22
    IdentityFile ~/.ssh/id_ed25519

Host production
    HostName 192.168.1.200
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```

然后逐个测试：

```bash
ssh -o BatchMode=yes \
    -o ConnectTimeout=5 \
    beta \
    "echo SSH_OK"
```

只有通过实际免密连接验证的服务器，才加入可选列表。

展示形式：

| 别名 | IP | 用户 | 端口 | 状态 |
|---|---|---|---|---|
| beta | 192.168.1.100 | root | 22 | 可连接 |
| production | 192.168.1.200 | deploy | 22 | 可连接 |

实际展示时，IP、用户名、端口均从 SSH 配置解析，不写死。

对于 ProxyJump、自定义端口、IdentityFile 等复杂 SSH 配置，应优先复用原始 SSH Host 别名，不自行拼接或覆盖连接参数。

## 3.3 新增免密服务器

服务器列表中必须提供新增服务器选项。

新增流程：

1. 执行人输入服务器 IP 或域名。
2. 输入 SSH 用户名。
3. 输入 SSH 端口。
4. AI 检查本地 SSH Key。
5. 如果没有 Key，引导执行人生成。
6. 引导执行人将公钥配置到目标服务器。
7. 执行免密连接测试。
8. 连接成功后引导保存 SSH Config。
9. 将服务器加入可选列表。

生成密钥：

```bash
ssh-keygen -t ed25519 -C "performance-diagnosis"
```

配置公钥：

```bash
ssh-copy-id -p 22 user@server
```

如果没有 `ssh-copy-id`，提供手动配置 `authorized_keys` 的操作指导。

安全要求：

- 不读取或上传 SSH 私钥。
- 不要求执行人将服务器密码提供给 AI。
- 不擅自修改现有 SSH Config。
- 新增配置前先展示修改内容。
- 首次连接时由执行人确认服务器 Host Key。
- 不通过关闭 Host Key 校验来绕过安全检查。
- 不自动修改远程服务器 SSH 安全策略。

## 3.4 服务器选择

每次诊断都由执行人明确选择目标服务器。

即使只有一台可连接服务器，也建议展示并要求确认，避免误操作生产环境。

# 四、Docker 容器识别与选择

## 4.1 Docker 环境检测

SSH 连接成功后，检查：

```bash
docker version
docker info
```

检查 Docker 是否正常运行，以及当前 SSH 用户是否具备 Docker 操作权限。

如果没有 Docker 权限，不应自动执行 sudo 提权，应提示执行人处理权限问题。

## 4.2 容器发现

获取运行中的容器：

```bash
docker ps --format \
  '{{.ID}}\t{{.Names}}\t{{.Image}}\t{{.Status}}'
```

针对每个运行中的容器，检查是否存在 Java 进程。

识别依据：

- Java 进程命令。
- Java 可执行文件路径。
- Jar 文件名称。
- JVM 主类。
- 进程启动参数。

不应仅通过镜像名称包含 Java 来判断容器是否运行 Java 服务。

## 4.3 容器选择

向执行人展示 Java 容器列表。

示例：

| 容器名称 | 镜像 | Java 服务 | 状态 |
|---|---|---|---|
| credamo-service | credamo/service:latest | credamo-service.jar | Running |
| credamo-admin-web | credamo/admin:latest | admin-web.jar | Running |
| credamo-task | credamo/task:latest | task.jar | Running |

如果存在多个匹配容器，必须由执行人选择。

一次只允许诊断一个指定容器。

禁止默认选择第一个匹配容器。

# 五、Java 进程识别与确认

## 5.1 PID 识别

进入目标容器的 PID Namespace，获取 Java 进程。

优先使用：

```bash
docker exec <container> jcmd -l
```

如果没有 jcmd，则通过 `/proc`、进程命令行等方式识别。

不能假设所有容器都有 ps、jcmd、bash 等命令。

## 5.2 多 JVM 处理

如果容器只有一个明确的 Java 业务进程，也需要展示该进程信息并要求确认。

如果存在多个 JVM，展示所有候选进程：

| PID | Java 主类/Jar | 启动时间 | 用户 |
|---|---|---|---|
| 1 | credamo-service.jar | 10:20 | root |
| 35 | another-service.jar | 10:25 | root |

由执行人明确选择目标 PID。

AI 不允许仅根据 PID 大小或进程顺序自动选择。

确认后记录：

- 服务器别名。
- 服务器 IP。
- 容器名称。
- 容器 ID。
- 容器内 PID。
- Java 版本。
- Java 启动命令。
- Jar 或主类名称。

后续所有诊断操作都必须绑定该目标，防止误 Attach。

如果容器重启、目标 PID 发生变化或容器 ID 不一致，必须停止当前任务并重新要求执行人确认。

# 六、Java 与 Arthas 兼容性检测

## 6.1 检测目标

在下载和启动 Arthas 之前，必须先检查目标容器的运行环境。

检测内容：

| 检测项 | 检测内容 |
|---|---|
| 操作系统 | Linux |
| CPU 架构 | x86_64 / aarch64 |
| Java 版本 | Java 8 等 |
| Java 路径 | 实际 JVM 使用的 Java 路径 |
| JVM PID | 容器内部 PID |
| JVM 用户 | 运行 JVM 的 UID/GID |
| Attach 能力 | 是否支持 JVM Attach |
| 文件系统 | 临时目录是否可写 |
| 磁盘空间 | 是否满足诊断文件需要 |
| 容器类型 | 普通容器 / 极简容器 |
| 安全权限 | 是否存在 Attach 相关限制 |
| 报告输出能力 | 是否存在可用的诊断文件输出目录 |

## 6.2 兼容性检查结果

分为三个状态：

**兼容：** 可以正常使用 Arthas。

**有条件兼容：** 需要调整执行方式，例如使用正确的用户、Java 路径或已有临时目录。

**不兼容：** 当前环境无法安全执行诊断，停止后续流程并提供原因。

## 6.3 重点处理的问题

- JRE 镜像缺少 Attach 所需组件。
- 容器缺少 Shell。
- JVM 用户和诊断用户不一致。
- `/tmp` 不可写。
- 容器安全策略限制 Attach。
- 容器 PID Namespace 与宿主机 PID 不一致。
- JVM 动态 Attach 被禁用。
- 容器内存和 CPU 限制。
- 容器文件系统启用了只读模式。
- 没有可用的诊断报告输出目录。

特别说明：

兼容性检测必须区分真正不可用和当前检测手段不可用。

例如没有 jcmd，不等于一定不能 Attach；没有 Shell，也不等于一定不能使用 Arthas。不能仅凭某一个检测命令失败就直接判定环境不兼容。

## 6.4 Attach 临时文件与报告输出目录分离

需要单独检测两类目录：

**Arthas 运行与 Attach 所需目录**

用于 Arthas 自身运行、JVM Attach 通信和必要的临时文件。

**诊断报告输出目录**

用于保存 Arthas 输出的文本、火焰图等文件。

两者可以是不同目录，不能默认认为只要报告目录可写，Attach 就一定可用。

# 七、Arthas 下载、缓存与远程部署

## 7.1 本地缓存目录

统一使用：

```text
~/.performance-diagnosis/
│
├── arthas/
│   ├── versions/
│   │   └── 3.x.x/
│   │       └── arthas-boot.jar
│   └── current-version
│
├── servers/
│
├── diagnostics/
│
├── logs/
│
└── temp/
```

说明：

- arthas：本地 Arthas 版本管理。
- servers：服务器相关的非敏感元数据。
- diagnostics：诊断结果。
- logs：本地 Skill 执行日志。
- temp：本地临时文件。

SSH 私钥不复制到此目录。

## 7.2 下载策略

首次使用：

1. 检查本地是否存在 Arthas。
2. 如果不存在，下载官方发行包。
3. 检查文件完整性。
4. 计算 SHA-256。
5. 记录版本信息。
6. 缓存到对应版本目录。

后续使用：

- 直接复用已缓存版本。
- 不重复下载。
- 不自动升级。
- 支持执行人手动切换或升级版本。

Arthas 版本需要经过 Java 8 环境验证后才能设为默认版本。

## 7.3 远程临时部署

采用：

**本地下载 → SCP 上传宿主机 → Docker CP 复制容器 → 容器内部启动。**

执行流程：

1. 本地检查 Arthas 版本。
2. 通过 SCP 上传到服务器临时目录。
3. 使用 Docker CP 复制到目标容器。
4. 在容器内部启动 Arthas。
5. Attach 目标 JVM。

不要求远程服务器或容器能够直接访问互联网。

临时目录建议使用唯一诊断任务 ID 隔离，避免不同诊断任务相互覆盖。

## 7.4 远程文件清理

诊断结束后：

- 确认 profiler 已停止。
- 结束当前诊断任务。
- 清理本次上传的 Arthas 文件。
- 清理无用临时文件。
- 保留本地诊断结果。

如果 Arthas 已经被其他执行人或其他会话使用，不能擅自关闭其他会话或删除其他任务的文件。

# 八、Arthas 统一执行引擎

## 8.1 设计目标

不让 AI 每次直接拼接 SSH、Docker、Arthas 命令。

而是封装一套统一执行脚本，由脚本负责：

- 连接远程服务器。
- 执行 Docker 命令。
- 启动 Arthas。
- Attach 目标 JVM。
- 执行 Arthas 命令。
- 保存命令输出。
- 返回执行结果。

AI 主要负责制定诊断策略、选择命令和分析结果。

## 8.2 命令封装建议

初步设计以下能力：

| 能力 | 作用 |
|---|---|
| prepare | 准备 Arthas |
| attach | Attach 目标 JVM |
| execute | 执行指定 Arthas 命令 |
| profiler-start | 启动性能采样 |
| profiler-stop | 停止采样并输出文件 |
| collect | 收集诊断数据 |
| status | 检查 Arthas 连接状态 |
| cleanup | 清理当前任务 |

具体实现时，优先使用 Arthas 支持的非交互式命令执行方式，避免依赖长期保持的交互式终端。

profiler 等持续任务需要独立的任务生命周期：

- 启动时生成任务 ID。
- 记录远程进程和会话状态。
- 到达采样时限后停止。
- 任务中断时能够检查远程状态。
- 确认任务结束后再执行清理。

## 8.3 执行脚本安全

- 服务器地址必须来自已确认的服务器配置。
- 容器 ID 必须来自已确认的容器选择。
- PID 必须来自已确认的 JVM 选择。
- 参数使用安全的参数传递方式。
- 不允许将未经验证的用户输入拼接为任意 Shell 命令。
- 对 Arthas 命令进行允许列表和风险等级校验。

# 九、诊断权限分级

生产环境默认只读诊断。

将所有操作分为 L1、L2、L3 三个级别。

## 9.1 L1：基础只读诊断

默认允许 AI 自动执行。

包括：

- dashboard
- thread
- jvm
- memory
- version
- JVM 基础信息采集
- Docker stats
- Docker inspect
- Docker logs
- Linux 系统资源采集

特点：

- 不修改业务数据。
- 不修改 JVM 配置。
- 不改变业务运行状态。
- 尽量采用低开销命令。

## 9.2 L2：受控性能诊断

在预设限制内允许 AI 自动执行。

包括：

- trace
- monitor
- watch
- profiler start / stop
- 火焰图生成
- 有范围限制的方法调用分析

执行要求：

- 明确诊断目标。
- 限制采样时间。
- 限制执行次数。
- 限制方法范围。
- 设置最大输出量。
- 记录开始和结束时间。
- 诊断完成后必须停止任务。

建议初始默认值：

| 操作 | 默认限制 |
|---|---|
| profiler 采样 | 30 秒以内 |
| trace | 限定方法和调用次数 |
| watch | 限定方法和观察次数 |
| monitor | 限定监控周期 |
| 并发诊断任务 | 同一 JVM 同时最多一个主动采样任务 |

这些限制后续可通过配置调整。

## 9.3 L3：高风险诊断

默认禁止自动执行。

包括：

- Heap Dump。
- 可能造成较大 STW 的操作。
- 动态修改 JVM 参数。
- 动态修改业务类。
- 可能影响目标 JVM 运行状态的操作。
- 其他需要额外权限或高资源消耗的操作。

即使执行人确认，也必须经过独立的风险检查。

第一版可以暂不实现 L3 命令执行，只支持识别风险并给出人工操作建议。

## 9.4 只读诊断的定义

本项目的只读不是指完全不产生任何系统副作用。

Attach Arthas、动态插桩、Profiler 采样都会产生一定的运行时开销，也可能在目标 JVM 中留下诊断组件。

本项目所说的只读是：

- 不修改业务数据库。
- 不修改业务文件。
- 不修改业务配置。
- 不修改业务代码。
- 不修改 JVM 启动参数。
- 不重启或停止业务容器。
- 不终止业务进程。
- 不执行自动修复。

允许在受控条件下执行必要的诊断操作，并在结束后清理诊断组件和临时文件。

## 9.5 生产只读边界

生产环境的只读约束是硬性限制，不允许 AI 为了完成诊断而绕过。

禁止：

- 动态添加 Docker Volume。
- 修改现有容器挂载。
- 重建容器。
- 修改 Docker 启动参数。
- 关闭容器只读文件系统。
- 自动提权绕过容器安全限制。
- 修改业务服务启动参数。

如果现有环境无法满足安全诊断条件，应停止对应诊断并报告原因。

# 十、问题分类与诊断策略

## 10.1 诊断入口

在成功连接目标 JVM 后，先让执行人选择问题类型。

第一版支持：

1. CPU 使用率高。
2. 接口响应慢。
3. 内存使用异常。
4. GC 频繁或 GC 停顿。
5. 线程阻塞或死锁。
6. 不确定原因，希望 AI 综合诊断。

支持一次选择一个主要问题类型。

如果综合诊断，AI 应先执行 L1 基础检查，再根据结果决定深入方向。

## 10.2 CPU 使用率高

目标：

- 定位 CPU 消耗较高的线程。
- 识别热点方法。
- 分析调用路径。
- 识别死循环、复杂计算和高频调用。

主要命令：

```text
dashboard
thread -n 10
profiler start
profiler stop --format md
profiler stop --format html
```

实际执行时，profiler start 和 stop 是同一个采样任务的两个阶段，不能重复启动。

分析内容：

- 热点方法。
- 调用树。
- 方法采样占比。
- 是否存在异常循环。
- 是否存在高频对象创建。
- 是否与业务代码相关。

## 10.3 接口响应慢

目标：

- 找到慢接口对应的方法。
- 分析方法调用耗时。
- 定位耗时较高的子方法。
- 区分本地计算和外部调用等待。

主要命令：

```text
dashboard
thread
trace
monitor
```

AI 需要先识别目标接口对应的方法，再使用 trace。

不能对所有接口、所有方法无限制执行 trace。

如果发现耗时主要发生在 Dubbo、数据库或 Redis 等外部调用，需要明确说明 Arthas 当前能够证明的调用耗时边界，不应仅凭调用耗时直接认定下游服务存在故障。

## 10.4 内存使用异常

目标：

- 判断堆内存使用情况。
- 分析内存增长。
- 识别高频对象分配。
- 判断是否存在内存泄漏迹象。

主要命令：

```text
dashboard
memory
jvm
profiler start --event alloc
profiler stop --format md
```

Heap Dump 属于 L3，第一版不自动执行。

需要区分：

- JVM Heap 使用量。
- Non-Heap 使用量。
- 容器实际内存使用量。
- Java 对象分配速率。

不能仅凭对象分配热点就认定存在内存泄漏。

## 10.5 GC 异常

目标：

- 检查 GC 次数。
- 检查 GC 时间。
- 分析 Full GC。
- 分析堆内存变化。
- 识别对象分配压力。

主要命令：

```text
dashboard
jvm
memory
```

必要时结合 JVM 已有 GC 日志分析。

不默认开启可能改变 JVM 参数的 GC 日志配置。

## 10.6 线程阻塞或死锁

目标：

- 检查线程状态。
- 定位 BLOCKED 线程。
- 检查锁竞争。
- 检查死锁。
- 分析线程池是否耗尽。

主要命令：

```text
thread
thread -b
dashboard
```

AI 需要区分：

- RUNNABLE
- BLOCKED
- WAITING
- TIMED_WAITING

不能简单把 WAITING 线程认定为异常。

## 10.7 综合诊断

当执行人不确定问题类型时：

1. 采集服务器资源。
2. 采集容器资源。
3. 采集 JVM 基础信息。
4. 查看线程状态。
5. 检查内存和 GC。
6. 根据异常特征选择深入诊断方向。

综合诊断不能一次性执行所有高开销命令。

# 十一、Docker 与 Linux 辅助信息采集

虽然 Arthas 是唯一的 JVM 诊断工具，但需要 Docker 和 Linux 原生命令提供外部环境信息。

## 11.1 Docker 信息

采集：

```bash
docker stats --no-stream
docker inspect
docker logs --tail 200
```

重点关注：

- CPU 使用率。
- 内存使用量。
- 内存限制。
- CPU 配额。
- OOM 状态。
- 容器重启次数。
- 容器启动时间。
- 容器运行状态。

## 11.2 Linux 信息

采集：

```bash
uptime
free -m
df -h
ss -s
```

必要时采集：

```bash
vmstat 1 5
```

关注：

- 系统负载。
- 可用内存。
- 磁盘空间。
- 网络连接数量。
- 系统资源压力。

## 11.3 容器资源与 JVM 资源联合分析

AI 必须同时考虑：

- 宿主机资源。
- 容器资源限制。
- JVM 内存使用。
- JVM GC 状态。

例如：

宿主机有 64GB 内存，但容器只有 2GB 内存限制。

不能因为宿主机内存充足，就判断 Java 服务不存在内存风险。

必要时结合 cgroup v1/v2 数据分析 CPU throttling、memory usage、OOM 等情况。

# 十二、诊断文件落盘与回传

## 12.1 核心问题

生产容器可能启用只读文件系统，或者 `/tmp` 不可写。

Arthas 生成的文本报告、火焰图等文件需要有可写的输出位置。

本项目不能为了生成报告而修改生产容器的原始配置。

因此，需要将业务环境只读和诊断文件写入分开处理。

**核心原则：允许使用容器已经存在的诊断临时空间，不允许为了诊断临时改变生产容器配置。**

## 12.2 目录分层

本地：

```text
~/.performance-diagnosis/
└── diagnostics/
    └── beta/
        └── credamo-service/
            └── <task-id>/
```

Docker 宿主机：

```text
/tmp/performance-diagnosis/<task-id>/
```

容器内部：

```text
/diagnostics/
```

其中，宿主机临时目录和容器内部目录是否对应，取决于容器是否已经存在可用挂载关系。

## 12.3 推荐输出策略

按照以下优先级处理。

### 方式 A：使用容器已有可写临时目录

优先检测容器现有的 `/tmp` 或其他可写挂载目录。

如果存在可用目录，在其中创建独立诊断子目录：

```text
/tmp/performance-diagnosis/<task-id>/
```

Arthas 报告写入该目录，再使用 `docker cp` 复制到宿主机。

### 方式 B：使用容器已有的宿主机挂载目录

如果容器已经挂载了宿主机目录，并且该目录对诊断进程可写，可以使用该目录输出报告。

需要确认：

- 挂载源路径。
- 容器内挂载目标路径。
- 挂载是否为只读。
- 目录权限和 UID/GID。
- 是否有足够的磁盘空间。

不能假设容器内某个路径一定对应宿主机临时目录。

### 方式 C：文本结果通过标准输出回传

部分 Arthas 命令可以通过非交互式执行方式将文本结果输出到标准输出。

此时可以由远程执行脚本捕获输出，再通过 SSH 回传本地。

这种方式适用于文本诊断结果。

火焰图等二进制文件不能简单依赖标准输出，应使用文件方式生成和传输。

### 方式 D：环境不支持文件输出

如果容器没有可用的可写临时目录，也没有已有可写挂载：

- 允许执行能够安全输出到标准输出的文本诊断。
- 不执行依赖文件落盘的诊断。
- 不生成无法安全保存的火焰图。
- 不修改容器配置。
- 在报告中说明缺失的环境条件。

## 12.4 只读容器特别约束

Docker 已运行的容器不能通过 `docker exec` 动态增加新的 Bind Mount。

因此：

- 不允许通过动态添加挂载解决问题。
- 不允许重建容器以增加诊断目录。
- 不允许修改 Docker 启动参数。
- 不允许关闭只读根文件系统。
- 不允许为了写报告而修改业务目录权限。

如果容器根文件系统只读，但已经存在可写的 `/tmp` 或其他挂载目录，可以继续诊断。

## 12.5 Arthas 运行目录与报告目录分离

需要分别管理：

1. Arthas 自身运行和 Attach 所需临时目录。
2. Arthas 诊断报告输出目录。

不能默认认为这两个目录必须相同。

兼容性检测必须分别验证：

- Attach 所需文件能否正常创建。
- Arthas 能否成功 Attach。
- 诊断报告能否正常生成。
- 报告是否可以复制回本地。

## 12.6 最终回传流程

```text
Arthas 生成诊断结果
       |
       v
容器内临时目录
       |
       v
docker cp 到宿主机
       |
       v
宿主机临时目录
       |
       v
SCP 回传本地
       |
       v
本地文件完整性校验
       |
       v
保存到诊断任务目录
       |
       v
清理远程临时文件
```

如果诊断文件本身已经写入容器与宿主机的现有共享目录，可以省略中间复制步骤，但必须验证实际文件位置和完整性。

## 12.7 本地结果目录

所有诊断结果统一保存到：

```text
~/.performance-diagnosis/diagnostics/
```

示例：

```text
diagnostics/
└── beta/
    └── credamo-service/
        └── 20261122-220000/
            │
            ├── 00-summary.md
            ├── 01-environment.md
            ├── 02-server-info.txt
            ├── 03-docker-info.txt
            ├── 04-jvm-info.txt
            ├── 05-dashboard.txt
            ├── 06-thread.txt
            ├── 07-memory.txt
            ├── 08-profiler.md
            ├── 09-flamegraph.html
            ├── 10-diagnostic-logs.txt
            └── diagnosis-report.md
```

根据实际执行的诊断类型生成文件，不要求每次都产生全部文件。

## 12.8 文件完整性

回传文件时：

1. 检查源文件是否存在。
2. 检查文件大小。
3. 计算 SHA-256。
4. 回传到本地。
5. 对本地文件计算 SHA-256。
6. 比较哈希值。
7. 校验成功后标记回传完成。

回传失败时保留远程文件，允许重新回传。

## 12.9 诊断报告格式

最终报告包含：

### 基础信息

- 诊断时间。
- 服务器 IP/别名。
- 容器名称。
- 容器 ID。
- JVM PID。
- Java 版本。
- Arthas 版本。
- 诊断问题类型。

### 环境状态

服务器、Docker、JVM 的资源和运行状态。

### 诊断过程

按时间顺序记录：

- 执行了什么命令。
- 为什么执行。
- 命令输出是什么。
- 发现了什么异常。
- 下一步为什么选择该诊断方向。

### 根因分析

每项根因必须包含：

- 问题描述。
- 证据。
- 相关方法或线程。
- 影响范围。
- 可信度。

### 优化建议

按优先级分类：

- 立即处理。
- 建议优化。
- 持续观察。

### 未解决问题

明确指出当前证据不足、无法确认的部分。

### 附件

列出原始日志、火焰图、线程信息等文件。

# 十三、诊断前后对比

增加性能数据对比能力。

当执行人提供优化前后两次诊断结果时，AI 可以进行对比。

建议关注：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 容器 CPU | 实际值 | 实际值 |
| 容器内存 | 实际值 | 实际值 |
| JVM Heap | 实际值 | 实际值 |
| GC 次数 | 实际值 | 实际值 |
| Full GC 时间 | 实际值 | 实际值 |
| 活跃线程 | 实际值 | 实际值 |
| 热点方法 | 实际值 | 实际值 |

注意：

- 对比数据应尽量保持相同的采样时间和业务负载条件。
- 不同时间段的数据不能直接视为严格的性能对比。
- AI 应标明对比条件和可能影响因素。

第一版只提供数据对比，不自动执行优化操作。

# 十四、异常处理与恢复机制

诊断流程必须考虑中途失败。

| 异常情况 | 处理策略 |
|---|---|
| SSH 连接失败 | 检查网络、端口、用户名、Key |
| Docker 不可用 | 停止诊断并提示原因 |
| 容器停止 | 终止当前任务 |
| 找不到 Java 进程 | 输出容器进程信息供确认 |
| 多个 JVM | 询问执行人选择 PID |
| Java 环境不兼容 | 输出检测报告并停止 |
| Arthas 下载失败 | 保留原始错误，不继续部署 |
| SCP 失败 | 重试并保留本地缓存 |
| Arthas Attach 失败 | 检查权限、PID、Attach 环境 |
| Arthas 命令失败 | 记录错误，判断是否可恢复 |
| SSH 中断 | 检查远程任务状态，避免重复启动 |
| 容器重启 | 终止当前诊断并要求重新确认目标 |
| Profiler 未正常停止 | 检查任务状态，执行受控清理 |
| 本地磁盘空间不足 | 停止文件采集并提示执行人 |
| 文件回传失败 | 保留远程文件，支持后续重新回传 |
| 诊断目录不可写 | 降级为标准输出文本诊断，文件型诊断停止 |
| 远程临时目录清理失败 | 保留任务记录并提示执行人处理 |

每个诊断任务应有唯一 ID。

例如：

```text
PD-20261122-220000
```

所有远程临时文件、诊断日志和本地文件都关联该 ID。

特别注意：AI 会话中断不代表远程命令已经停止。因此必须能够识别和恢复未完成的诊断任务。

清理操作只能针对当前任务创建的文件和进程，不能误删其他诊断任务或其他执行人的文件。

# 十五、安全设计

## 15.1 核心安全要求

生产环境默认只读诊断。

禁止自动执行：

- 修改业务代码。
- 修改业务配置。
- 修改数据库。
- 修改 Redis 数据。
- 重启容器。
- 停止容器。
- Kill Java 进程。
- 修改 JVM 参数。
- 动态修改业务类。
- 修改服务器安全配置。
- 修改 Docker 容器配置。

## 15.2 文件安全

- SSH 私钥不上传。
- 不读取不必要的业务敏感文件。
- 不将完整环境变量直接写入诊断报告。
- 诊断日志中的 Token、密码、密钥需要脱敏。
- Heap Dump 默认不采集。
- 诊断文件设置合理权限。
- 远程临时文件在确认回传成功后清理。
- 本地诊断文件默认仅当前用户可访问。

## 15.3 命令安全

- 所有服务器必须经过执行人确认。
- 所有容器必须经过执行人确认。
- 所有多个 JVM 场景必须确认 PID。
- 命令参数必须经过校验。
- 禁止任意 Shell 命令执行。
- 只允许执行诊断命令白名单。
- L2 操作需要受到时长、次数、范围限制。
- L3 操作默认禁止。

## 15.4 生产环境只读保证

只读诊断不仅是 Skill 的提示词约束，还应当落实到脚本执行层。

具体要求：

1. 对远程命令实行白名单。
2. 将业务修改命令列入明确的禁止列表。
3. 不向诊断脚本提供重启、停止、Kill 等操作入口。
4. 不自动提权。
5. 不修改容器配置。
6. 不修改业务目录。
7. 不修改 JVM 参数。
8. 对所有 L2 操作进行时间和资源约束。

如果执行环境无法保证只读边界，则停止操作。

Skill 负责指导 Agent，脚本负责确定性操作，两者不要混淆。

# 十九、正式技术决策清单

以下作为 V1.0 开发约束，后续如需变更应明确调整设计。

| 编号 | 事项 | 最终决策 |
|---|---|---|
| D1 | Arthas 版本 | 固定经过 Java 8 验证的版本，不自动追踪 latest |
| D2 | SSH 配置管理 | 直接复用 `~/.ssh/config`，不维护第二套服务器配置 |
| D3 | Arthas 远程部署 | 本地缓存 + SCP + Docker CP |
| D4 | Arthas 执行方式 | 非交互式命令执行，持续任务独立管理 |
| D5 | 容器兼容性 | 首版支持具备必要 Attach 能力的 Docker Java 容器 |
| D6 | L3 功能 | 首版只识别和提示，不自动执行高风险操作 |
| D7 | 诊断文件 | 全部尽可能回传本地，保留原始输出 |
| D8 | 远程临时目录 | 使用唯一诊断任务 ID 隔离 |
| D9 | 无 Shell 容器 | 首版不保证支持，无法安全执行时明确报告不兼容 |
| D10 | 采样时长 | 默认最多 30 秒，可配置 |
| D11 | 诊断并发 | 单个 JVM 同一时间最多一个主动采样任务 |
| D12 | 文件保留 | 本地长期保存；远程临时文件在成功回传、校验后清理 |
| D13 | 生产只读 | 不修改业务代码、业务配置、业务数据，不重启或停止业务服务 |
| D14 | 临时文件写入 | 只使用容器已有的可写临时目录或挂载目录 |
| D15 | 只读容器 | 不动态添加挂载、不重建容器、不关闭只读文件系统 |
| D16 | 输出目录不可写 | 文本结果尽可能通过标准输出回传；文件型诊断无法执行时明确提示 |
| D17 | Attach 兼容性 | 检测 JVM 用户、PID Namespace、Attach 通信及临时目录条件 |
| D18 | 异常恢复 | SSH 中断或 Agent 会话结束后，能够识别未完成任务并进行受控清理 |

# 二十、最终预期使用体验

执行人只需要向 AI 提出：

> 帮我排查 beta 环境 credamo-service 的 CPU 使用率为什么持续偏高。

AI 自动执行以下流程：

**第一步：选择服务器**

展示本地已经配置免密登录的服务器：

- beta
- production
- test

执行人选择 beta。

**第二步：选择容器**

AI 连接服务器，发现：

- credamo-service
- credamo-admin-web
- credamo-task

执行人选择 credamo-service。

**第三步：确认 JVM**

AI 发现：

```text
PID: 1
Service: credamo-service.jar
Java: 1.8.0_xxx
```

执行人确认。

**第四步：兼容性检查**

AI 检查 Java、Attach、容器权限、临时目录和磁盘空间，确认 Arthas 可以运行。

如果容器根文件系统只读，AI 继续检查是否存在已有可写临时目录。

如果没有可用目录，则只执行支持安全输出的文本诊断，不尝试修改容器配置。

**第五步：准备 Arthas**

检查本地缓存，必要时下载，随后上传到远程容器。

**第六步：选择问题类型**

执行人选择 CPU 使用率高。

**第七步：自主诊断**

AI：

- 检查 JVM 状态。
- 查看高 CPU 线程。
- 使用 Arthas profiler 采样。
- 生成火焰图（环境支持时）。
- 分析热点方法。
- 必要时结合 trace 深入分析。

**第八步：输出报告**

AI 将全部可获取的原始结果回传本地，并生成：

`~/.performance-diagnosis/diagnostics/beta/credamo-service/<task-id>/diagnosis-report.md`

报告说明：

- CPU 异常原因。
- 具体热点方法。
- 相关代码位置（如果能够访问源码）。
- 诊断证据。
- 优化建议。
- 仍然存在的不确定性。
- 哪些诊断因环境限制未能执行。

整个过程不修改生产业务代码、数据、配置，不重启或停止业务服务，不改变容器原始配置。

# 二十一、总结

本项目的核心不是简单地让 AI 执行 Arthas 命令，而是建立一套完整、可控、可追溯的线上性能诊断工作流。

第一版的核心执行链路确定为：

**本地 SSH 服务器发现 → 服务器选择 → Docker 容器选择 → JVM PID 确认 → 兼容性检测 → Arthas 本地缓存与远程部署 → 自主诊断 → 结果回传 → 生成报告。**

核心技术约束：

- 仅支持 Docker 中运行的 Java 服务。
- 仅使用 Arthas 作为 JVM 诊断工具。
- 仅通过 SSH 免密连接远程服务器。
- 本地 Arthas 缓存统一位于 `~/.performance-diagnosis`。
- 每次只诊断一个指定 Java 容器。
- 多 JVM 时由执行人确认 PID。
- 诊断权限分为 L1、L2、L3。
- 生产环境默认只读诊断。
- 只使用容器现有可写临时目录，不改变容器原始配置。
- 所有可获取的结果统一保存并回传本地。
- AI 自主制定诊断策略，但不能突破权限边界。

**最终目标：让不熟悉 Arthas 的开发人员，也能够通过自然语言完成一次完整、专业、可复现的 Java 线上性能排查。**
